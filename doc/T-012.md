## Problem and evidence limits

The pinned `pryanik_simplified.stl` has 3,796 triangles and 13 confirmed
self-intersection pairs; [T-003](T-003.md) retains independent overlap evidence.
Its original source remains invalid. Existing tolerance welding/replay does not
establish an intersection repair. Full Pryaniks are separate accepted assets,
not automatically authoritative parents or substitutes for this source.
OpenVDB is an evaluation candidate only: neither dependency selection, Windows
qualification nor a valid reconstructed derivative has been demonstrated.
Its [mesh-to-volume](https://www.openvdb.org/documentation/doxygen/MeshToVolume_8h.html)
and [volume-to-mesh](https://www.openvdb.org/documentation/doxygen/VolumeToMesh_8h.html)
documentation are evaluation inputs, not acceptance evidence for these fixtures.

## Bounded outcome

Evaluate an existing C++ library for a bounded mesh-to-volume/reconstructed-mesh
proposal, then implement the selected supported repair path with before/after
diagnostics, preview and explicit Accept/Reject. Keep the existing weld proposal
available and label its actual capabilities. Source bytes are preserved exactly.
Repair pitch is an independent physical setting with documented resource limits;
packing pitch and display LOD do not define the repair or its accepted geometry.

A reconstructed full-resolution mesh becomes authoritative only after native
solid validation and explicit acceptance. Thereafter packing, restore and export
use that accepted derivative and recorded source-to-local mapping. Changing search
pitch must not regenerate or alter the accepted repair. Reject invalid or
indeterminate proposals; previews and closed-edge counts do not authorize a solid.
No silent cavity filling, topology substitution, convex hull, unit change or
resize-to-fit. Topology changes are shown in the proposal and accepted explicitly.
No bespoke general repair kernel, arbitrary open-surface reconstruction promise,
GPU dependency, automatic acceptance or unmeasured certified-deviation claim.

## Decisions and compatibility to freeze

Evaluate the actual simplified Pryanik and small analytic repair adversaries before
selection. Record Windows build/package cost, license/notices, transitive runtime
dependencies, version pin and supported input/resource envelope. Select the library
only after evidence; an unavailable/unqualified candidate is not a passing stub.
Freeze the solid interpretation for intersections/overlapping shells and cavity
preservation, reconstruction method, triangulation, repair pitch and tolerances.
Declare unsupported ambiguity rather than guessing the user's intended volume.

Record an architect/geometry decision and compatibility assessment before behavior
or schema changes. Specify source/proposal/accepted hashes, parameters, library/
algorithm version, units/frame, seed where relevant, diagnostics and acceptance
decision. Extend the weld-only replay contract deliberately; old weld records
continue loading, unsupported new recipes fail clearly and arbitrary stored PLY
bytes cannot supply authorization. Freeze deterministic replay or a versioned
verified-reconstruction policy with explicit limits; never silently reinterpret it.

Define bounded preview/result ownership, cancellation and cache invalidation;
repair-memory estimates include library volume/tree and reconstruction workspace.
Report bounds, components/cavities, triangles, displacement and meaningful volume
changes. Label sampled deviation as sampled, with method/resolution; it is not
a certified global error bound. Warn concretely about observed lost detail/gaps.

## Parallel implementation and ownership

Use one branch/PR and the [two-worker execution rules](MILESTONES.md#parallel-agent-execution).
The native owner handles the actual library, `engine/pack_geometry/`, dependency
integration and native repair/resource tests. The integration owner handles
`engine/pack_io/`, `engine/cli/`, `desktop/`, schemas/generated types and
replay/journey tests. Assign build/dependency files exclusively before edits.
Candidate evaluation and recipe/authority compatibility are serial decisions;
after a useful native proposal and shared contract exist, finish the bounded
native adapter and desktop/persistence workflow concurrently. Final acceptance
uses the integrated native result, not a fixture standing in for the library.

Library research can run earlier in an available worker slot as isolated scratch
evaluation, without a dependent product branch or production dependency changes.
Keep findings/inputs in `.local/`; this does not close any T012 acceptance gate.
The product branch and integration still await T-010's merged Stop/lifetime
contract. CPU implementation and uncontended measurements retain priority.

## Observable acceptance

- **T012-A1 — selected useful repair.** Pin source hashes and produce a native-valid
  derivative of the simplified Pryanik using the selected documented library path.
  Record parameters/resources and before/after geometry. An unmodified original
  remains invalid; weld controls or a more detailed error cannot pass this gate.
- **T012-A2 — explicit authority.** Diagnose, generate, preview, reject and accept
  through the real desktop. Reject leaves the source and prior accepted result
  unchanged. Before acceptance the proposal cannot pack/export; only valid native
  acceptance creates the new authoritative identity. Never publish indeterminate.
- **T012-A3 — semantics and metrics.** Analytic intersection, gap, thin-feature,
  cavity, component and ambiguous-shell fixtures demonstrate supported behavior
  and specific rejection. Show actual geometric changes before acceptance;
  preserve physical scale/frame. Independently check metrics where exact answers
  exist and distinguish sample estimates from certified bounds.
- **T012-A4 — separate resolutions.** Change packing pitch and display LOD after
  accepting a repair; accepted hash/full-resolution mesh remain unchanged.
  Change repair pitch or recipe: create a new proposal requiring new validation
  and acceptance. Source bytes/hashes remain unchanged in every case.
- **T012-A5 — provenance and replay.** Save, move to a Unicode/spaced directory,
  Open and replay/verify the accepted derivative through production native paths.
  Preserve source, accepted bytes, recipe/version/decision, frame and ordered poses.
  Tampered source/mesh/recipe/hash, unsupported versions and incompatible algorithms
  reject clearly without losing the previous complete state. Legacy weld still works.
- **T012-A6 — native packing/export.** Pack the accepted simplified-Pryanik repair
  at a frozen supported profile, independently validate every pose and reread
  exported binary STL coordinates/copy map. Export the accepted derivative with
  its source provenance; do not substitute the original or display approximation.
  Establish at least one independently valid placement for the positive profile
  and require the solver to retain at least that nonempty count; empty export
  cannot establish useful repair support.
- **T012-A7 — resources and failure.** Before integration freeze host-specific
  repair time/memory bounds from one warmup and five repeated bounded evaluations,
  with the finest supported repair pitch in mm, supported input profile and explicit
  memory/work limits. Exercise
  cancellation, allocation/output failure and failed proposal publication. Meet
  declared caps, retain complete state and preserve the T-011 Stop contract.

## TDD, verification and delivery

Begin with actual-library evaluation evidence and a practical missing-proposal/
acceptance/replay test. Observe the intended product red behavior before integration;
library demo success alone is neither native acceptance nor a product green run.
Implement the smallest supported proposal path, then refactor with affected gates
passing. Generate shared types from schemas after the compatibility decision.
Inspect available runners; record actual commands instead of invented repair APIs.
Run affected Debug/Release import, solid validity, repair replay, packing/export,
archives, desktop and resource checks, plus dependency/package/notices validation.
Retain full logs and rejected/failed proposals in `.local/t012/`; commit a compact
T012-A1–A7 ledger with hashes, recipe, quantitative bounds and observed outcomes.
Obtain architect review for dependency/contracts and critical geometry review for
solid interpretation, accepted authority and repair uncertainty. If no bounded
candidate produces an unambiguous valid repair, stop for scope reassessment with
the evidence; an external repair route may help the user but does not complete
the in-app repair gate. Update status only after actual qualification and user merge.
