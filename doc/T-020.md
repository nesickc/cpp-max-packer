# T-020: Auto fallback and actual Radeon qualification

Status: planned; no implementation or passing evidence claimed.
Proposed branch: `feature/AT-16-auto-gpu-fallback` (not created).
Prerequisites: [T-018](T-018.md) and [T-019](T-019.md), merged into `main`.
Start the branch only after those prerequisites and this planning change merge.
Follow [MILESTONES.md](MILESTONES.md); T-021 live viewing is not a prerequisite.

## Scope and boundary

Qualify Auto device selection, allocation/device-loss recovery and a feasible
CPU continuation from the last validated checkpoint. Record backend transitions,
remaining budget and reset search state where required. Preserve explicit CPU
and Vulkan behavior. This is M5 backend/resource acceptance on actual Windows
Radeon hardware; final full-v1 benchmark/distribution qualification is T-022/T-023.
Fallback cannot shrink geometry, gaps or a manual pitch to manufacture success.

## Governing requirements

SYS-03, SOL-05/SOL-06, UI-03, DATA-01/DATA-02 and QA-02; AT-02/AT-12/AT-13/AT-16
subsets. Canonical spec §§4.3, 6.6, 8.2–8.4 and 10.1 govern.
[ADR 0011](../spec/decisions/0011-cpu-first-follow-up.md) and shared evidence apply.

## Observable acceptance

1. **T020-A1:** Auto selects Vulkan only after feature queries, startup self-test
   and complete memory preflight. Missing loader, unsuitable device, failed test
   or insufficient resources select CPU; report actual backend and corrective details.
2. **T020-A2:** Explicit CPU avoids Vulkan initialization. Explicit unavailable
   Vulkan returns `GPU_UNAVAILABLE` rather than silently changing backend.
   Repeat the AT-02 pinned `benchy_small` CPU/Radeon paths on recorded hardware.
3. **T020-A3:** Inject device allocation failure and loss during planning, compute
   and an unfinished trial. Discard that trial, load/revalidate the latest complete
   checkpoint and continue on CPU when feasible; no invalid revision is published.
4. **T020-A4:** Preserve count/poses, physical constraints and stable surviving IDs
   across fallback. Record backend/device/driver changes, run segments, remaining
   Start-origin budget and explicit search-state reset; never imply exact GPU-state replay.
5. **T020-A5:** Preflight CPU recovery at the same manual pitch. Evict caches and
   reduce batches before termination; if CPU cannot fit, preserve the valid result
   and return a specific resource termination. Automatic pitch changes before
   a new job are visible; in-flight fallback cannot silently alter a manual setting.
6. **T020-A6:** Exercise host/device failure, shared-memory accounting, full output
   disk and unresponsive native work. Respect declared caps or terminate gracefully;
   Stop acknowledges within 250 ms, ordinary safe Stop within 5 s, and termination
   is offered after 10 s with usable UI and recoverable checkpoint.
7. **T020-A7:** Re-run the GPU integer-oracle/error-injection gates and independent
   result/export validation on the qualified Radeon. Publish exact OS/device/driver,
   build/dependency/thread settings, transitions and failures; no invented GPU results.

## Tests, evidence and review

Use spec-linked red/green state-transition/failure cases, real checkpoint recovery
and actual Windows Radeon observations. Include failures at each ownership boundary;
a mocked fallback response cannot establish recoverability. Retain raw logs,
counts/poses, times and memory in `.local/t020/`; shared sampling rules apply.
Freeze backend/recovery contracts with an architect. Device-loss synchronization,
checkpoint admission and consequential resource uncertainty need critical review.

## Open decisions and compatibility

Define device-loss ownership, safe cleanup, CPU feasibility, checkpoint compatibility
and transition/error DTOs before edits. Preserve older explicit CPU projects and
clear unsupported-version behavior. M5 is complete only when its actual AT-02,
GPU AT-12 and AT-16 evidence is assembled; this plan or an Auto toggle is insufficient.
