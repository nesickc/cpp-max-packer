## Problem and evidence limits

The desktop resolves CPU thread count 1 and `solve` rejects another count.
Pocketfft is compiled with threading, cache and vector paths disabled; its audited
workspace bound assumes those modes. A thread-count control alone changes no work.
T-009's field/resource fixes precede this ticket: parallelizing quadratic work or
replicating unsupported fields cannot establish a useful scalable implementation.
No speed ratio or dominant parallel stage is yet measured for the new baseline.

## Bounded outcome

Use T-009's pinned Release measurements to select one useful first parallel path:
FFT transforms, field tiles/distance passes, orientation preparation, or independent
validation work. Implement a bounded CPU worker policy and expose the actual
resolved thread count, supported range and resource estimate in native/UI state.
Keep authoritative accepted solids shared and immutable. Publication and incumbent
admission remain ordered, synchronized and independently validated.

The threading slice must improve a practical CPU workload's end-to-end execution,
not merely a microbenchmark. Additional parallel layers are follow-ups unless
measurements establish they are necessary to achieve the frozen acceptance target.
No GPU, new search policy/orientation catalog, live viewer streaming or SIMD claim.
SIMD, FFT plan caching and nested threading require separate measured admission.

Prepared-asset reuse, a Start-origin deadline, phase reporting and cancellable
preparation are included exactly as specified by T-011. Threading and preparation
have separate performance targets and acceptance records; improvement in one
cannot mask a failure in the other. Durable jobs/recovery remain later work.

The reviewed T-009 dependency also requires reducing repeated field/raster work
enough to finish the Ulamok cube catalog and the full practical workflows under
unchanged aggregate caps. Its retained-copy rasterization alone has a lower bound
of 3,246,096,384 units against the 1,300,000,000 cap; threading or coarsening alone
cannot fix this. Close the original T009-A2/A3/A6 obligations with an actual
supported spectral run retaining at least 36, verified pitch advice, and all
three successful desktop/export journeys. Keep the 24-orientation first-pass
check; do not count a retained resource failure as success. See ADR 0012 and
T-009's failed 4/16 mm probes before selecting the bounded field-work change.
The retained 36-copy desktop result additionally hits `EXPORT_IMPORT_WORK_LIMIT`
during checked STL export. Preserve this distinct A6 reproducer and diagnose the
packed-mesh import/validation work; successful JSON round trips do not close it.

## Parallel implementation and ownership

One primary coordinates one branch/PR and at most two leaf workers. Freeze a
single architecture/compatibility decision for worker lifetime, immutable prepared
assets, cancellation/deadlines, publication and aggregate memory before parallel
edits. Give each worker exact files and tests; see the
[shared execution rules](MILESTONES.md#parallel-agent-execution).

| Work lane | Exclusive default write scope | Delivery |
| --- | --- | --- |
| Native runtime | `engine/pack_compute/`, `engine/pack_solver/`, required preparation/cancellation internals in `engine/pack_geometry/`, and their native tests | Selected measured parallel kernel, bounded workers/scratch, native prepared-asset APIs, cancellation safe points and numerical/resource evidence |
| Product integration | `engine/cli/`, `engine/pack_io/`, `desktop/`, `spec/schemas/`, contract tooling and protocol/journey tests | Shared settings/timing/error compatibility, accepted-asset lifecycle/reuse, Start/Stop transport, thread controls, phase feedback and project/export journeys |

One designated worker lands agreed schema/shared-interface changes first; both
consume that committed contract. The integration worker alone edits `solve.cpp`,
`desktop.cpp`, result metadata and generated types. If the chosen native design
requires adapter changes, hand them to that owner. Assign root build files and
any new shared helper explicitly before edits; never give both workers the same
file. Native internals and integration can then proceed concurrently against the
agreed interface. Fakes may unblock development, but final gates use real native
work. The primary coordinates integration and assigns fixes rather than adding
a third implementation lane.

Retain T-009's baseline before optimization. Measure threading with preparation
state fixed, and reuse at a fixed thread count; also report combined end-to-end
behavior. Performance samples run serially on the host. One focused critical
review covers the combined lifetime/cancellation/authority boundary; subsequent
reviews address changes or unresolved findings, not an automatic duplicate pass.

## Decisions and compatibility to freeze

Record an architect decision before parallel edits: selected lane, worker lifetime,
thread-count default/range, scheduling granularity, nested-library threading policy,
queue bound, cancellation checkpoints and serial incumbent-publication owner.
Memory admission includes every simultaneous worker's scratch/plans/staging,
retained buffers, validation and viewer reserve. Avoid nested oversubscription;
do not launch multiple full-memory correlations without aggregate preflight.
Revise pocketfft workspace accounting/tests before enabling its threaded mode.

Record actual thread configuration and scheduling/version policy in resolved
settings/provenance. Preserve legacy results' thread-count interpretation and
single-thread execution. Freeze schema/version and old-project loading behavior
before changing shared fields; generate UI types from the accepted schema.
Same-build, same-thread fixed-work reproducibility is required. Cross-thread-count
identical heuristic poses are not promised unless deliberately implemented/tested.
Threading cannot alter physical dimensions, clearance, accepted authority or pitch.

## Observable acceptance

- **T010-A1 — real configuration.** Native execution accepts the documented
  supported thread counts and reports the actual count. Unsupported values fail
  specifically. Desktop pending settings and old results remain clearly associated.
  Demonstrate parallel execution at the selected real kernel, not a mocked pool.
- **T010-A2 — numerical correctness.** Run direct correlation/proximity oracles
  and their error envelopes at 1/2/4 threads. Cover asymmetric extents, rotations,
  nonzero origins, halos and uncertain cells. Every published result is independently
  native-valid; numeric failure does not become a feasibility conclusion.
- **T010-A3 — reproducibility.** Repeat fixed-work runs on the same build/host
  and each identical thread configuration; counts and ordered transforms reproduce.
  Record seeds, scheduling policy, counters and failed repetitions. Compare quality
  across thread counts separately rather than assuming identical search histories.
- **T010-A4 — aggregate resources.** Exercise bounded queues, simultaneous
  worker scratch and a cap immediately below admission. Inject allocation failure
  while workers are active; no cap is exceeded or invalid trial published. Record
  measured peak memory alongside the conservative estimate and explain its margin.
- **T010-A5 — Stop and races.** Stop during each newly parallel heavy stage,
  shutdown and worker failure. Acknowledge within 250 ms; ordinary qualified cases
  reach safe stop within 5 s. Workers join before memory release or terminal state;
  late work cannot publish into a new operation. Retain the latest valid result.
- **T010-A6 — measured speed.** Pin analytic, Ulamok and the supported full-Pryanik
  profiles from T-009. Retain one warmup and five serial Release samples at 1/2/4 threads and,
  if hardware permits, one additional bounded count. Before optimization, freeze
  numerical median targets for the selected phase and fixed-work end-to-end time,
  with a maximum accepted memory increase. Meet both speed targets on at least
  one practical profile; document other profiles and regressions without omission.
- **T010-A7 — product regression.** Preserve Ulamok's qualified physical lower
  bound, original-invalid rejection and the existing import/Save/move/Open/export
  paths. Validate every compared pose set and independently reread retained exports.
  Report wall-clock count/quality as well as fixed-work speed; less search is not
  evidence of faster computation.

## TDD, verification and delivery

Start with a practical unsupported-thread or missing-parallel-execution reproducer
and observable resource/reproducibility checks. Observe the intended red behavior;
do not manufacture a failing timing test from an unmeasured speed assumption.
Implement one admitted parallel lane, then refactor with affected checks passing.
Resolve ownership before concurrent worker edits; workers do not design incompatible
thread pools in separate modules. Keep architecture and benchmark decisions small.
Use existing configured runners after inspection; record actual commands rather
than proposed tool names. Run affected Debug/Release compute, solver, controls,
allocation, contracts and desktop cases. Broaden for failures or shared-state risk.
Retain complete logs, thread/memory measurements and failed samples in `.local/t010/`;
T-011 evidence may remain in `.local/t011/`. Commit one delivery ledger mapping
T010-A1–A7 and T011-A1–A7 to the integrated revision and frozen baseline/targets.
Shared journey/control runs may satisfy both sheets when the ledger identifies
each actual assertion; do not rerun identical checks solely for a second label.
Obtain focused critical review of concurrency, resource ownership and cancellation;
route unresolved numerical concerns explicitly. Do not substitute repeated trials
or race-free mock tests for review and real native evidence.
Update status with implemented versus measured scope, open one ready PR to `main`,
and wait for user review/testing/merge before dependent T-012 product integration.
A threading-only implementation cannot close this combined delivery.
